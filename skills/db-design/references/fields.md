# Field reference

Every field of a jjf database design document: what it accepts, what it
rejects, and the conventions to follow. The enum values below are reproduced in
full so that a value can be written correctly the first time.

Back to [SKILL.md](../SKILL.md).

## Identifiers

Applies to `database.name`, `tables[].name`, `columns[].name`,
`references.table`, and every constraint and index name.

- Pattern `^[A-Za-z_][A-Za-z0-9_]*$`, 1 to 128 characters
- ASCII letters, digits and underscores only, and never a leading digit
- Rejected: hyphens (`order-lines`), schema-qualified names (`public.users`),
  quoted identifiers, and non-ASCII physical names. Non-ASCII names belong in
  `logicalName`
- Conventions: plural snake_case tables (`order_items`), singular snake_case
  columns (`unit_price`), `pk_<table>`, `uq_<table>_<columns>`,
  `fk_<table>_<target>`, `ix_<table>_<columns>`. **A different convention already
  in the document wins.**

## `logicalName`

- Free text, any language, 1 to 255 characters
- **Required** on tables and columns; optional on `database`
- This is where a Japanese or otherwise non-ASCII name goes

## `description`

- Free text, up to 2000 characters; the empty string is allowed
- Newlines are fine — the Excel cell wraps
- Put here everything the schema cannot express: business rules, units, the set
  of values a column may hold, operational caveats

## `type`

- Pattern `^[A-Za-z][A-Za-z0-9_ ]*$`, 1 to 64 characters
- ASCII letters, digits, underscores and spaces only. Uppercase by convention
- Accepted: `VARCHAR`, `BIGINT`, `NUMERIC`, `TIMESTAMP WITH TIME ZONE`,
  `DOUBLE PRECISION`, `VARCHAR2`, `DATETIME2`, `NVARCHAR`
- Rejected: `VARCHAR(30)` and `TIMESTAMP(3)` (parentheses), `INT[]` (brackets),
  `4BYTE_INT` (leading digit), `CHARACTER-VARYING` (hyphen)
- A type this notation cannot express — a PostgreSQL array type, for instance —
  goes in as its element type, with the rest stated in `description`
- See [types.md](types.md) for the recommended spelling per DBMS

## `length` / `precision` / `scale`

- `length`: declared length of a character or binary type. Integer, minimum 1
- `precision`: total significant digits of a numeric type. Integer, minimum 1
- `scale`: digits after the decimal point. Integer, minimum 0. **Writing `scale`
  requires `precision`** — `scale` alone is a structural error
- Which to use: `length` for `VARCHAR` / `CHAR` / `VARBINARY`, `precision` plus
  `scale` for `NUMERIC` / `DECIMAL`
- Types without a declared size — `INTEGER`, `BIGINT`, `TEXT`, `DATE`, `BOOLEAN`
  — carry none of the three. Leaving all three out is the normal case, not an
  omission to be filled in

## `nullable`

- **Boolean, never omitted.** `true` accepts NULL, `false` is NOT NULL
- The string `"true"` is a type error. Do not quote it
- Set `false` on every column of the primary key. `jjf validate` warns when a
  primary key column is declared nullable

## `default`

- **String only**, at most 255 characters. Numbers and booleans are written as
  strings too (`"default": "0"`, `"default": "true"`)
- The value is **SQL expression text, copied verbatim** into the DEFAULT
  clause. `jjf` never evaluates it; it only checks that it reads as an
  expression
- String literals carry their quotes: `"default": "'pending'"`, or
  `"default": "''"` for the empty string
- Functions go in as written: `"default": "CURRENT_TIMESTAMP"`,
  `"default": "now()"`, `"default": "gen_random_uuid()"`
- **No DEFAULT clause means no `default` key.** Omit it entirely
- Write `"default": "NULL"` only to state `DEFAULT NULL` explicitly
- `"default": ""` means "a DEFAULT of the empty SQL expression", which is
  meaningless. For a default of the empty string write `"''"`. `jjf validate`
  warns about it
- An unquoted word is warned about too: `"default": "now"` is a *column
  reference* in SQL, not the string `now` — PostgreSQL rejects it with "cannot
  use column reference in DEFAULT expression". Write `"'now'"` for the string,
  `"now()"` for the function. Keyword constants such as `CURRENT_TIMESTAMP`
  need nothing

## `autoIncrement`

- Boolean, default `false`. Covers `IDENTITY`, `AUTO_INCREMENT`, `SERIAL` and
  sequence-backed columns
- Omit it when `false`
- Record the mechanism (`SERIAL` versus `GENERATED BY DEFAULT AS IDENTITY`, say)
  in `description` if it matters

## `dbms` — exactly these six values

```text
"PostgreSQL"  "MySQL"  "MariaDB"  "SQLite"  "Oracle"  "SQLServer"
```

Matched exactly, case included. `"postgres"`, `"MSSQL"` and `"SQL Server"` all
fail validation.

The field is descriptive for every command except `jjf export ddl`, which
requires it and writes the dialect it names. `"PostgreSQL"` and `"MySQL"` are
written; the other four are refused with exit code 2, because a dialect ships
only once an importer and a live-server round trip can check it end to end. See
[ddl-output.md](ddl-output.md).

## `onUpdate` / `onDelete` — exactly these five values

```text
"CASCADE"  "RESTRICT"  "SET NULL"  "SET DEFAULT"  "NO ACTION"
```

All uppercase. `SET NULL` and `SET DEFAULT` use **one ASCII space**, not an
underscore. Omitting the field means no clause is emitted, leaving the DBMS
default behaviour.

## `unique` on `indexes[]`

- Boolean, default `false`. `true` for a unique index
- A **unique constraint** belongs in `uniqueKeys`, not in `indexes` with
  `unique: true`. Never state the same thing in both places

## Keys and indexes

| Object | Required | Optional |
| --- | --- | --- |
| `primaryKey` | `columns` | `name` |
| `uniqueKeys[]` | `columns` | `name` |
| `foreignKeys[]` | `columns`, `references` | `name`, `onUpdate`, `onDelete` |
| `references` | `table`, `columns` | — |
| `indexes[]` | `name`, `columns` | `unique` |

`indexes[].name` is the one name that is **required** — the others may be left to
the DBMS, though a design document reads better with them written out.

Every `columns` list needs at least one entry and rejects duplicate names. In a
foreign key, `columns` and `references.columns` must agree in **count and order**
— a composite key's ordering is meaningful.
